## 這次要決定什麼（30 秒版）

PHASE-010 做「**稽核檢視與回歸**」：管理員多一頁可以查「誰、什麼時候、對誰、做了什麼、改前改後是什麼」；再把前面各期已經在寫的稽核紀錄**回頭驗一遍是不是真的都有寫**；順帶把「有歷史資料的帳號不准刪」這條規則完整驗證。

要批准的是：**12 個設計決策（D1~D12，每個都附推薦）＋ 4 個高風險 Task 的事前批准 ＋ 3 條「條件 AC」要不要做**。全照推薦就回「照推薦」。

**但有 4 條建議您親自過目**（見下表），其中兩條是這期挖出來的**新問題**。

## 務必親自過目的 4 條

| # | 白話問題 | 推薦與代價 | 您的裁定 |
|---|---|---|---|
| **D5** ★ | **挖到一個真缺口**：規則說「有歷史資料的帳號不准刪、請改用停用」，但實際上資料庫有 **6 條**「有資料就不准刪」的關卡，程式**只檢查了 2 條**。剩下 3 條（做過管理操作的人、上傳過照片的人、幫別人建過草稿的人）現在刪下去會直接**噴系統錯誤 500**，而不是好好地說「請改用停用」 | 推薦 **(c) 兩邊都補**（前面擋 ＋ 後面兜底）。**代價請您明示接受：補完之後，凡是曾經建過帳號／改過參數的管理員，就永遠不能被永久刪除了，只能停用。**這正是「有歷史就拒刪」的原意，但不可刪的範圍會明顯變大 | |
| **D11** ★ | **挖到第二個不對稱**：作廢、參數、油耗、代操作這些事件的稽核，是**跟主操作綁在同一筆交易**裡（一起成功或一起失敗）；但**帳號類**（新增／停用／密碼重設／刪除）的稽核是「寫失敗就**默默吞掉**」——操作成功了，稽核紀錄可能悄悄沒寫進去 | 推薦 **(a) 這期不動、記錄下來移交下一期**。理由：這期主軸是「檢視與回歸」，改這個要動到帳號授權端點的失敗行為（稽核寫失敗＝整個操作失敗，管理員會看到 500 要重試）。**但如果您認為「稽核可能悄悄遺失」不能接受，就選 (b)，我會補一個高風險 Task 進去** | |
| **D3** | **「改前改後」要怎麼呈現？** 稽核裡存的摘要格式有四種不同長相（有的是單一值、有的是「改前/改後」一組、油耗那種還是巢狀的）。以前的複審已經警告過：**處理不好畫面會出現 `[object Object]` 這種亂碼** | 推薦 **(c)**：後端統一攤平成「欄位／改前／改後」三欄再送給前端，前端只負責顯示。附帶問題：欄位名會是英文（如 `annualTotalKm`），**要不要在前端加一層中文對照表？**（成本低，建議一併決定） | |
| **D8** | **拖了三期的老問題結案**：稽核的「操作類型」清單要不要再加新的值？（例如「報表產生」「建立修正版」各給一個獨立類型） | 推薦 **(a) 不加，維持現在 10 個值**——我逐條比對過需求文件列的 7 類事件，**現有 10 個值全都對得上，沒有缺**。而且不加的話**這期完全不用改資料庫**。建議這次直接結案，以後別再逐期重議 | |

## Step-by-step 檢核步驟

1. **（2 分鐘）** 讀 Spec §1「目標與非目標」——這期做什麼、不做什麼（**不重寫稽核寫入邏輯、不碰備份/效能**）。
2. **（5 分鐘）** 看上表 4 條，逐條給裁定（D5 與 D11 是新發現，請特別留意）。
3. **（4 分鐘）** 掃其餘 8 條 D（Spec §16，皆有推薦，不同意就點名）：
   - **D1** 端點放哪個檔（推薦：新開 `audit/routes.ts`）
   - **D2** 篩選可以用哪些條件（推薦：類型／日期區間／操作者／受影響對象，四項）
   - **D4** 稽核只有管理員看得到（推薦：是）
   - **D6** 要不要順手補「錯誤訊息可能帶出程式檔案路徑」這個縱深漏洞（推薦：補。**但上一期終審給的草案原文在檔案裡找不到了，我是照摘要重寫的**——如果您記得原案不同請說）
   - **D7** 五項技術債要收幾項（推薦：收 2 項小的 ＋ 2 條註解更正；另 3 項移下一期，含「E2E 型別檢查」那個 76 個錯誤的大坑）
   - **D9** 時間怎麼顯示（推薦：後端給標準格式、前端顯示台北時間，跟列印版一致）
   - **D10** 新頁面放哪（推薦：首頁管理員區多一個「稽核紀錄」入口）
   - **D12** 加一道「稽核紀錄不准被改被刪」的自動檢查（推薦：加，純測試零風險）
4. **（1 分鐘）** **4 項高風險 Task 事前批准**：T1（摘要攤平：稽核對外揭露的唯一出口）／T2（查詢端點與權限）／T3（稽核齊備回歸）／T5（帳號拒刪回歸）。批准即事前批准，後續不再逐項請示。
   > 註：若 D8 改選「新增類型值」，會多一個高風險 Task（要動資料庫），變成 5 項。
5. **（1 分鐘）** **3 條條件 AC 的取捨**：AC-14（D5 的補洞）／AC-21（D6 的漏洞收斂）／AC-22（D7 的技術債）——隨對應的 D 一起決定即可。
6. **（1 分鐘）** **來源標記確認**（治理要求）：Spec §0.2 末段列出哪些驗收條件是「需求文件原文直接來的」、哪些是「把既有語意撐大」、哪些是「我建議加的」。撐大與建議加的部分請掃一眼有無異議。
7. 回覆裁定（AskUserQuestion 已備妥）。
