### A. 測試決定性（使用者方向①）

**AC-01 — B-30 併發之終局語意封閉**（依 §16 **D1**）〔來源：建議新增〕

- **(a)** `phase6-maintenance-complete.test.ts` 之 B-30 迴圈（現行 `CONCURRENCY_ROUNDS = 12`）在**每一輪**皆須：完成方之拒絕碼落於**依 D1 裁定之封閉集合**內，且**恆非 500**。
- **(b)** 終局狀態之二分法維持不變（完成方勝出 → 附件 `LINKED` ∧ `totalAmount` 非 null；刪除方勝出 → `status=DRAFT` ∧ `totalAmount` null）；**新增第三分支**（若 D1 裁定 (a)/(c)）：完成方得 `503` 時，終局須為 `DRAFT` ∧ `totalAmount` null ∧ 附件狀態與該輪刪除方之回應一致（**不得**出現「503 但已寫入快照」之殘留）。
- **(c)** **503 路徑之鑑別力自證**：以**故障注入**（`isRetryableTransactionConflict` 恆真之替身，或重試上限暫改為 0）構造一次確定性之重試耗盡，斷言得 `503` ＋ `SERVICE_UNAVAILABLE` ＋ **DB 零寫入**（`Application.status` 仍 `DRAFT`、`snapshot*` 全 null）。〔核銷 `PROJECT_STATE.md` :417 AR-2「503 重試耗盡全 Phase 無測試」〕
- **(d)** 【若 D1 裁定 (b)/(c)】競態緩解之**前後對照物證**須記入 Handoff：同一 harness 於修改前後各跑 **N ≥ 30** 輪之 503 出現次數；**不得**以「重跑沒紅」代替物證。
- **(e)** 本 Task 對 `backend/src` 之 diff **僅限** D1 裁定所授權之檔案；若 D1 = (a)（純測試面），`backend/src` diff **必須為 0**。

**AC-02 — E2E 共享參數軸播種日單調性機械守門格**（依 §16 **D2**）〔來源：建議新增〕

- **(a)** 存在一具**不需 DB、不需瀏覽器**之機械守門，掃描 `e2e/**/*.spec.ts` 之全部參數版本播種日字面（油價 `FuelPriceVersion.effectiveFrom`、ETC、折舊、使用者油耗），並對每一條**共享時間軸**（＝以「參數類別（＋油種）」為鍵）建立其播種日之全序清單。
- **(b)** **下界不變式（硬）**：全 `e2e/` 之任一參數播種日**不得 ≤ `1999-05-05`**（＝`travel-application.spec.ts` :62 `NO_PARAM_TRIP_DATE`；該檔情境 2「缺參數路徑」倚賴此不變式）。違反即紅，錯誤訊息須指出**肇事檔、行號、該日期、被破壞之不變式名稱**。
- **(c)** **哨兵不變式**：宣告為「哨兵播種者」之檔案（現行恰一：`audit-log.spec.ts` 之 `FUEL_PRICE_EFFECTIVE_FROM = "2010-01-01"`）於其軸上之播種日，須**嚴格早於**同軸其他任一檔之播種日。新檔在同軸播下更早日期即紅。
- **(d)** **鑑別力自證（三型 mutant，於測試內以合成字串執行，不改真實檔）**：①注入一筆 `1990-01-01` 之合成播種 → (b) 必紅；②注入一筆與哨兵同軸且更早之合成播種 → (c) 必紅；③注入一筆**同軸但晚於哨兵**之合成播種 → **兩式皆綠**（防過寬——新 spec 之合法播種不得被誤擋）。
- **(e)** **掃描器之涵蓋自證**：以「全 `e2e/` 現行檔案清單」與「掃描器實際解析到的檔案清單」做 `toEqual`——新增 E2E 檔而未被掃描到即紅（防止守門對新檔靜默失效）。
- **(f)** 守門之**錯誤訊息**須逐字包含修法指引（「請改用晚於哨兵日之播種日，或於本守門之軸註冊表新增一條軸並說明」），使後續 Phase 之開發者不需回讀本 Spec 即可自解。

### B. 附件暫存清理（BE-US-25⑤⑥；使用者方向②）

**AC-03 — 「無引用」判定之封閉來源集**（依 §16 **D4**）〔來源：US 逐字（BE-US-25⑥）〕

- **(a)** 存在一個具體之 `HasReferenceQuery` 實作（`lifecycle-service.ts` :134 既有介面契約），其查詢之引用來源**恰等於**一份**封閉宣告清單**；清單以**常數**表達，並有機械斷言證明「實作所查之來源集 ＝ 該常數」。
- **(b)** 該清單之**完整性守門**：以 `information_schema`／Prisma DMMF 列舉「今日資料層中任何可能指向 `Attachment` 之欄位」，與清單逐項比對；**新增一個指向附件之欄位而未入清單即必紅**（沿 `PHASE-010.md` AC-14(a) 之 FK 完整性守門形狀）。
  - **實查基線（本 Spec 給定，供 Gate 覆核）**：`schema.prisma` 全案**無任何 FK 指向 `Attachment`**；引用關係為**弱引用且方向相反**（`Attachment.refType`／`refId` → 容器）。故清單之實際判定面為：①`status`（`LINKED` 恆受保護）②`refType`／`refId` 所指容器之**存在性**③`AuditLog.summary` 之 JSON 內是否出現該附件 id（BE-US-25⑥ 逐字含「稽核資料引用」）④`Report`／`VoidedReportFile`（**實查：兩表零 `attachmentId` 欄位**——PDF 內嵌位元組而非引用，故結構性不構成引用；此判斷須寫入常數之註解並由 (b) 之列舉守門背書）。
- **(c)** **`AuditLog.summary` 面之處置**須明確：若 D4 裁定納入，則以 `jsonb` 內容比對（不得以字串 `LIKE` 掃全表——效能與誤判）；若裁定不納入，須有**負向記載型 `it`** 明示「本判定刻意不含稽核面」並載明理由（沿 `phase10-error-handler-leak.test.ts` 之「已知不可及」記載型格）。
- **(d)** 判定函式**零副作用**：對 DB 只讀（結構斷言：該模組零 `create`／`update`／`delete`／`deleteMany`／`upsert`）。

**AC-04 — 清理之 dry-run 唯讀模式**〔來源：既有語意擴張（PRD :543）〕

- **(a)** 清理程序具備 **dry-run 模式**，於該模式下：DB 零寫入（前後 `Attachment` 全表逐欄快照全等）、storage 零刪除（前後物件鍵集合全等）。
- **(b)** dry-run 輸出**候選清單**，每筆含：附件 id、`status`、`createdAt`、已逾期時數、判定為「無引用」之依據（AC-03 清單之逐項結果）。**輸出不得含**：`storageKey`、`originalFilename`、`ownerId`／`uploaderId` 之外顯值以外的任何個資（沿 `DATA_FLOW.md` :565③ 之日誌禁字）。
- **(c)** dry-run 與實際執行**共用同一判定路徑**（結構斷言：兩者呼叫同一個判定函式，非兩份複本）——**防「dry-run 說安全、實跑刪錯」**。
- **(d)** dry-run 為**冪等**：連跑兩次輸出全等。

**AC-05 — 清理執行之三向行為**（依 §16 **D3**／**D6**）〔來源：US 逐字（BE-US-25⑤⑥）〕

- **(a)** **可刪**：`status=TEMP` ∧ 無引用 ∧ `now - createdAt` **嚴格大於** `ATTACHMENT_TEMP_TTL_HOURS`（預設 24）→ DB 列刪除 ＋ storage 之 `original` 與 `thumb`（若在場）位元組刪除；刪除後 `storage.exists()` 皆為 false。**含一格以「修正版草稿刪除後之複本」構造**（`KNOWN_ISSUES.md` :100 §5-5）。
- **(b)** **不得刪（三型逐一）**：①`status=LINKED`（不論多舊）②`status=TEMP` 但有引用（依 AC-03 之來源逐型各一格）③`status=TEMP` 無引用但**恰在 TTL 邊界**（`elapsed = TTL` 不刪——`isEligibleForCleanup` :352 現行為嚴格大於，本 AC 釘死該邊界）。
- **(c)** **刪除順序與失敗語意**：DB 列刪除**先於** storage 位元組刪除（沿 `lifecycle-service.ts` :23 既有 TEMP DELETE 語意）；storage 刪除失敗**不得**回滾 DB 刪除（該檔已不可達），但須計入失敗計數並記一行零內容日誌（`{ stage, attachmentId }`，**不得**記 `storageKey`）。
- **(d)** **鑑別力自證（mutant）**：①把「嚴格大於」改為「大於等於」→ (b)③ 必紅；②把 `LINKED` 之保護移除 → (b)① 必紅；③把引用查詢恆回 false → (b)② 全數必紅。
- **(e)** **零弱化守門**：本 Task 不得修改 `isEligibleForCleanup` 之既有語意（其既有單元測試零改動即為證據）。

**AC-06 — 清理之觸發、批次與可觀測性**（依 §16 **D3**／**D6**）〔來源：建議新增〕

- **(a)** 清理之**觸發形式恰為 D3 所裁定者**，並有結構斷言證明**未同時存在第二條觸發路徑**（防「腳本 ＋ 忘了關的 interval」雙跑）。
- **(b)** 單次執行有**批次上限**（可由 env 設定，預設值於 §8 給定）；超過上限之候選留待下次執行，**不得**在單次執行中無界處理。
- **(c)** 單次執行輸出**摘要**：掃描筆數／候選筆數／實刪筆數／失敗筆數／耗時。摘要**不含**任何個資與 storage key。
- **(d)** **部分失敗不中止**：其中一筆刪除失敗時，其餘候選仍照常處理；行程結束碼依 D6 裁定（**推薦**：有失敗即非零，供外部排程告警）。

### C. HTTPS / Cookie / 反向代理

**AC-09 — Cookie 安全屬性**（依 §16 **D7**）〔來源：US 逐字（NFR-US-11②）〕

- **(a)** `buildCookieOptions`／`buildClearCookieOptions`（`auth/routes.ts` :51／:64）為**純函式**且以 `isProduction` 為參數——**production 分支可被單元測試直接覆蓋，無須設定 `process.env.NODE_ENV=production`**（該設定會撞 INFRA-001 globalSetup 之 fail-closed 護欄，`global-setup.ts` :304）。
- **(b)** `isProduction = true` 時，Cookie 屬性**逐項**為 D7 所裁定之集合；以 `toEqual` 封閉比對（多一屬性／少一屬性皆必紅）。
- **(c)** `isProduction = false` 時，既有 `auth.test.ts` :350 之 `AC-28`（`HttpOnly` ∧ `SameSite=Lax` ∧ `Path=/` ∧ **無** `Secure`）**逐字仍綠且零修改**——非 production 行為不得因本 Phase 改變（開發環境 HTTP 下若加 `Secure`，登入將整體失效）。
- **(d)** **wire 面驗證**：以 production 選項建 server 實例（注入而非改 env）發一次登入，`Set-Cookie` 標頭逐屬性斷言；**同時**斷言 Cookie 值本身**零出現於任何日誌行**（沿 `logger.ts` :11-29 之 redact 清單 ＋ `log-security.test.ts` 既有形狀）。
- **(e)** 【若 D7 裁定含 `__Host-` 前綴】須同批確認 `SESSION_COOKIE_NAME` 之預設值變更對 `auth/middleware.ts` :90／:101 之 `clearCookie` 路徑無破壞，且 `__Host-` 之三項硬性前提（`Secure` ∧ `Path=/` ∧ **無** `Domain`）逐條有斷言。

**AC-10 — HTTPS 與反向代理標頭**（依 §16 **D8**）〔來源：US 逐字（NFR-US-11①）〕

- **(a)** 應用層之「是否為安全連線」判定**恰有一個來源**（結構斷言：全 `backend/src` 之 `x-forwarded-proto`／`req.protocol` 取值恰一處）。
- **(b)** 依 D8 裁定：**(b-1)** 若採 Fastify `trustProxy`，其設定值**不得**為無條件 `true`（會使任何用戶端可偽造 `X-Forwarded-For`／`X-Forwarded-Proto`），須為**具體代理來源**或 hop 數；該值由 env 提供且有預設；**(b-2)** 若採「不信任、由平台保證」，須有記載型 `it` 明示該假設與其失效後果。
- **(c)** **偽造防護之鑑別力**：以帶 `X-Forwarded-Proto: https` 之請求打**未設定信任**之實例，斷言應用**不因此**認定為安全連線（防「信任預設打開」）。
- **(d)** `frontend/nginx.conf` 現行已轉發 `X-Forwarded-Proto $scheme`（實查 :24）——本 AC 不改該檔之轉發行為；若 D8 需調整，屬 infra 設定變更，須逐行說明。
- **(e)** **HTTP → HTTPS 導向**之落點依 D8 裁定（平台層／nginx 層／應用層擇一），並有記載型 `it` 載明「本專案之導向落於何層、應用層為何不重複做」。

### F. 持久化與分離部署驗證

**AC-15 — 容器重建不失資料**〔來源：US 逐字（NFR-US-02②／04①／06③／07①）〕

- **(a)** 存在一份**可重複執行之驗證程序**（腳本 ＋ Runbook 章節），其步驟為：起 stack → 播種一筆含附件之已完成申請並產生 PDF → 記錄三項指紋（DB 之申請 id ＋ 金額、附件 `contentHash` 或位元組長度、PDF `contentHash`）→ `docker compose down`（**不加 `-v`**）→ `docker compose up` → 重新驗證三項指紋**逐一全等**。
- **(b)** **附件**於重建後**仍可經授權端點取回**且位元組全等。
- **(c)** **正式 PDF** 於重建後仍可下載且 `contentHash` 全等。
- **(d)** **反向對照（鑑別力）**：`docker compose down -v`（刪 volume）後同一驗證**必然失敗**——此對照須實跑並記入 Handoff（證明驗證程序不是恆真）。
- **(e)** 驗證程序之**執行證據**（逐步輸出）記入 Handoff；程序本身納入 `docs/verification/WALKTHROUGH-PHASE-011-INTEGRATION.md`。

**AC-16 — 三面分離部署**〔來源：US 逐字（NFR-US-01①／02①／03①②／04①／06①②）〕

- **(a)** 由乾淨狀態以 `docker compose up --build` 啟動三服務，全部達到 healthy；前端可經 `/api` 打到後端、後端可連 DB。
- **(b)** **單面重建之獨立性**：①只重建前端（`docker compose build frontend && docker compose up -d frontend`）→ 後端與 DB **容器 id 不變**（機械證據：`docker compose ps -q` 前後比對）且業務資料不變；②只重建後端 → 前端映像檔 id 不變且 DB 資料不變。
- **(c)** **DB 服務可替換**之結構性證據：後端對 DB 之取用恰經 `DATABASE_URL` 一處（AC-11(d) 已涵蓋），故「改用其他 PostgreSQL 服務」為純設定變更——以記載型 `it` 明示，**不實跑外部服務**。
- **(d)** 執行證據記入 Handoff 並納入整合 Gate 走查腳本。

### G. 效能

**AC-17 — 單點回應時間目標**（依 §16 **D10**）〔來源：US 逐字（NFR-US-14①~④）＋既有語意擴張（(e)(f)(g)）〕

- **(a)** 一般列表與詳情查詢 **≤ 2 s**（涵蓋：申請列表、申請詳情、管理員全域列表）。
- **(b)** 日期區間里程統計 **≤ 3 s**。**本項之實測值同時作為 §16 D17（索引補強）之裁定輸入**（PHASE-005 D9(a) 搭配條件）。
- **(c)** 一般表單提交（草稿儲存、完成申請；**不含**大型附件上傳等待）**≤ 2 s**。
- **(d)** 正式 PDF 產生 **≤ 10 s**。
- **(e)** **作廢（含作廢版 PDF 產生）≤ 10 s**〔`KNOWN_ISSUES.md` :98 §5-3〕。
- **(f)** **建立修正版（含附件複製）≤ 5 s**〔同上〕。
- **(g)** **稽核列表查詢 ≤ 2 s**〔`KNOWN_ISSUES.md` :113 §5-15③〕。
- **(h)** **量測條件須逐條載明並隨數據交付**：資料規模（各表列數）、硬體／環境（本機 compose／dev／CI）、量測方式（冷啟／暖機、取樣數、統計量）。**單次取樣不算數**：每個目標至少 **N ≥ 5** 次，報告中位數與最大值，**以最大值對照目標**。
- **(i)** 未達標之項目**不得**以放寬目標處理——須列為 §17 已知限制並附建議（如索引、查詢改寫），由人類裁定是否本期優化。

**AC-18 — 約 20 併發之可用性**（依 §16 **D10**）〔來源：US 逐字（NFR-US-14⑤）〕

- **(a)** 以 **20 個併發客戶端**執行「一般系統功能」之混合負載（登入後之列表查詢 ＋ 詳情 ＋ 草稿儲存），持續 **≥ 30 s** 或 **≥ 200 次請求**（以 D10 裁定為準）。
- **(b)** **可用性判準（機械）**：①`5xx` 比率 **＝ 0**（含 `503`——若出現 `503`，須逐筆歸因並列 §17）②`4xx` 僅限預期之業務碼③p95 回應時間對照 AC-17 之對應目標。
- **(c)** 量測**環境與資料規模**同 AC-17(h) 逐條載明。
- **(d)** **本項之量測手法無專案先例**——須依 §11.6 之 spike 結論執行；spike 失敗時之替代路徑亦見該節。

### H. 備份

**AC-19 — 備份涵蓋範圍**（依 §16 **D11**）〔來源：US 逐字（NFR-US-12①②）〕

- **(a)** 備份腳本產生之產物涵蓋 **PostgreSQL 全庫**（含 `AuditLog` 與其 `summary` `jsonb`〔`KNOWN_ISSUES.md` :113 §5-15①〕、含 `_prisma_migrations`）。
- **(b)** 涵蓋**附件 storage**（`ATTACHMENT_STORAGE_ROOT` 下 `att/` 前綴之全部物件，含 `original` 與 `thumb`，**含修正版複製之副本**）。
- **(c)** 涵蓋**報表 storage**（`REPORT_STORAGE_ROOT` 下 `rpt/` 前綴之全部物件，**含 `VoidedReportFile` 之 `void` 物件**）〔`KNOWN_ISSUES.md` :96 §5-1〕。
- **(d)** **涵蓋完整性之機械斷言**：備份後，以 DB 之 `Attachment.storageKey`／`thumbnailKey`／`Report.storageKey`／`VoidedReportFile.storageKey` 四來源之聯集，逐鍵確認**皆在備份產物內**（缺一即紅）。
- **(e)** 備份產物含**清單檔（manifest）**：時間戳、涵蓋範圍、各部分之位元組數與雜湊、產生此備份之工具版本。
- **(f)** 備份為**唯讀操作**：執行前後正式資料之 DB 與 storage 逐項全等。

**AC-20 — 保留 ≥14 天**〔來源：US 逐字（NFR-US-12③）〕

- **(a)** 保留策略以 **env 參數**表達（預設 **14**），且腳本之清理邏輯為：**保留最近 N 天內之全部備份**，超過者才刪。
- **(b)** **邊界**：恰 N 天之備份**保留**（嚴格大於才刪——與 AC-05(b)③ 同一取邊界紀律）。
- **(c)** **保護下限**：`N < 14` 之設定值須**拒絕**（fail-fast，訊息含變數名），使 US 之硬性下限不可被設定繞過。
- **(d)** **零備份時不誤刪**：目錄為空或僅有一份備份時，清理不得刪除任何檔案（防「清理把唯一備份刪掉」）。
- **(e)** **鑑別力（mutant）**：把「嚴格大於」改為「大於等於」→ (b) 必紅；把下限守門移除 → (c) 必紅。

**AC-21 — 不與正式同主機／磁碟**（依 §16 **D12**）〔來源：US 逐字（NFR-US-12⑤）〕

- **(a)** 備份腳本之**目的地由 env 指定**，且腳本**拒絕**目的地落於「正式資料所在之路徑樹內」——具體判準：目的地之正規化絕對路徑**不得**是 `ATTACHMENT_STORAGE_ROOT`／`REPORT_STORAGE_ROOT`／PostgreSQL data 目錄之**任一祖先或後裔**。
- **(b)** 拒絕時之**訊息**須明確指出違反之項目（含變數名，**不含**完整路徑值——沿日誌禁字紀律，僅顯示相對關係）。
- **(c)** **鑑別力（三格）**：①目的地 ＝ storage root 之子目錄 → 必拒②目的地 ＝ storage root 之父目錄 → 必拒③目的地為獨立路徑 → 必受理。
- **(d)** **「不同磁碟／異地」之更強保證**依 D12 裁定；**無論裁定何者，(a) 之路徑樹守門為下限，不得被取代**。
- **(e)** Runbook 須載明正式環境之異地保存**為部署時人工設定**（PRD :526）及其驗收方式。

**AC-22 — 備份產物不含明文 secrets**〔來源：既有語意擴張〕

- **(a)** 備份產物（含 manifest 與任何中繼檔）之內容經 AC-12 之同一掃描器掃描，零命中。
- **(b)** 備份與還原腳本之**日誌輸出**零命中：連線字串、密碼、Cookie／token、`storageKey` 完整值、volume 絕對路徑（沿 `DATA_FLOW.md` :565③ 七類禁字）。
- **(c)** 腳本取得 DB 憑證之方式**不得**經命令列參數（會出現在行程表）——須經環境變數或 `.pgpass` 同等機制；以結構斷言釘死。

### I. 還原驗證

**AC-23 — 還原驗證之三項確認**（依 §16 **D13**）〔來源：US 逐字（NFR-US-12④／NFR-US-13①）〕

- **(a)** **資料庫可開啟**：還原至**隔離目標**（獨立 schema／獨立容器，**絕不**覆寫正式）後，可建立連線並查詢；`_prisma_migrations` 之最後一筆與備份當時一致。
- **(b)** **附件可讀取**：自還原之 storage 抽樣 **≥3** 個附件物件（含至少一個 `thumb`、至少一個修正版副本），位元組雜湊與備份 manifest 全等。
- **(c)** **主要資料關聯存在**：逐項確認（**清單化，機械可查**）——①`Application` ↔ `TravelApplication`／`MaintenanceApplication`／`DepreciationApplication` 之 1:1 無孤兒②`TripSegment` → `TravelApplication` 無孤兒③`Report` → `Application` 無孤兒④`VoidedReportFile` → `Report` 無孤兒⑤`Attachment.refType`／`refId` 之 `LINKED` 列其容器存在⑥`AuditLog.actorId` 指向存在之 `User`⑦`Session.userId` 指向存在之 `User`。
- **(d)** **還原不得污染正式**：整個還原驗證流程之前後，正式 DB 與 storage 逐項全等（機械前後快照）。

**AC-24 — 還原驗證失敗之紀錄**〔來源：US 逐字（NFR-US-13②）〕

- **(d)** 紀錄檔之內容經 AC-12 掃描器零命中。

### 3.1 附件暫存清理（維運流程，非使用者流程）

```
維運人員／排程 →（依 D3）觸發清理程序（dry-run）→

```

```
  → 目的地路徑樹守門（AC-21(a)）→ 不合格即拒絕、非零結束碼
  → ①DB 全庫 dump ②att/ 前綴物件 ③rpt/ 前綴物件

  → 涵蓋完整性自檢（AC-19(d)：四來源鍵集皆在產物內）
  → 保留期清理（保留最近 N 天，N ≥ 14；恰 N 天保留）
  → 摘要輸出（零敏感內容）
```

### 3.3 每月還原驗證（維運流程）

```
排程／人工 → 還原驗證腳本 →
  → 取最近一份備份 → 還原至【隔離目標】（獨立 schema／容器；絕不覆寫正式）
  → ①DB 可開啟 ＋ _prisma_migrations 尾筆相符
  → ②附件抽樣 ≥3（含 thumb、含修正版副本）位元組雜湊對 manifest 全等
  → ③關聯完整性七項逐一（AC-23(c)）
  → 全通過 → 成功紀錄；任一失敗 → 失敗紀錄（階段 ＋ 摘要）＋ 非零結束碼
  → 前後正式 DB 與 storage 逐項全等（AC-23(d)）
```

### 3.4 部署硬化之驗證（整合 Gate 流程）

```
維運人員 → docker compose up --build → 三服務 healthy
  → 播種一筆含附件之已完成申請 ＋ 產生 PDF → 記錄三指紋
  → docker compose down（不加 -v）→ up → 三指紋逐一全等（AC-15）
  → 只重建前端／只重建後端 → 另兩面容器 id 不變、資料不變（AC-16(b)）
  → 反向對照：down -v → 同一驗證必然失敗（AC-15(d)）
```

## 11. 測試策略

### 11.0 測試紀律（強制，寫入每個 Task Packet）

1. **TDD**：先寫必失敗之測試；不得刪除、弱化、skip 既有測試換綠燈。
2. **零弱化**：AC-26 寫入每個 Task 之 Done When。
3. **不可逆操作之紅燈物證義務**：凡涉刪除之 Task（清理、保留期清理、孤兒處置），**修復前之危險行為**與**修復後之安全行為**皆須有物證記入 Handoff；「跑起來沒刪錯」不算物證，須有 mutant 證明守門承重。

## 14. Rollback

| 情境 | 處置 |
|---|---|
| **Spec 未批准／方向翻轉** | 分支未合併，直接棄用 `phase-011` 分支；`main` 零影響 |
| **Task 層失敗** | 單一 atomic commit 還原（`git revert`）；本 Phase **核心 14 Task 皆為新增檔或既有檔之加法式修改** |
| **清理排程（T3／T4）** | **設定層可逆**：依 D3，`ATTACHMENT_CLEANUP_ENABLED=false`／停止外部排程即停用；程式面 `git revert`。**但已刪除之附件不可復原**——故 PRD :543 之「先 dry-run 再啟用」為**硬性前置**（AC-25(g) 入 Runbook），且**啟用前之最後保險為備份**（見 §15.1 硬性排程約束 #1） |
| **孤兒處置（T6，條件）** | 若 D5 裁定「只報告不刪」→ **零不可逆面**；若裁定「納入刪除」→ 保護期為緩衝，仍不可復原 |
| **Cookie／代理（T7）** | 純設定與純程式變更，`git revert` 即回復；**但期間已發出之 Cookie 屬性不追溯改變**（使用者重新登入後生效），Runbook 須載明 |
| **env 硬化（T8）** | 純加法；若新增必要變數導致既有部署啟動失敗，回滾為「移除該必要性」——**須同批回滾 `.env.example` 與 compose**，否則 AC-13 之機械守門會紅 |
| **健康檢查（T9）** | 若新探針誤判導致部署平台反覆重啟，**回滾路徑為移除該探針**；D9 之裁定須計入此風險（見 §16 D9 影響欄） |
| **持久化驗證（T10）／效能量測（T11）** | 純新增腳本與文件，零產品面影響（`backend/src` 零 diff） |
| **備份／還原（T12／T13）** | 純新增腳本；**還原驗證恆對隔離目標執行**（AC-23(d)），正式面零風險；備份目的地守門（AC-21）為防呆下限 |
| **migration（僅 D6／D17 裁定時）** | `CREATE INDEX` → `DROP INDEX` 可逆；**`ALTER TYPE ADD VALUE` 不可逆**（PostgreSQL 限制），保留為未使用值屬無害（沿 PHASE-004 先例）——此為 D6 之主要代價 |
| **條件 Task（T15~T19）** | 皆為獨立 commit、與主線零檔案交集（**T16 除外**——其觸既有 `phase10-error-handler-leak.test.ts`），逐一可 revert |

### D1 — B-30 併發之 `503` 第三態如何收斂　**【使用者可見行為 ＋ 錯誤契約】**

**為什麼要決定**：PR #19 合併批准時人類已**接受**該 flaky 並登記「候選本期收斂」（`PROJECT_STATE.md` :71）——「候選」不等於「必須」。實查根因：`completeMaintenanceApplication` 於序列化衝突重試 6 次後拋 `SERVICE_UNAVAILABLE`／`503`（`maintenance-service.ts` :1218 一帶），而 B-30 之斷言只許 `[400, 403, 409]`（`phase6-maintenance-complete.test.ts` :880）。**`503` 本身是產品既有且刻意設計之契約**（重試耗盡之誠實回應），**測試斷言才是缺口**。是否要「消除 `503`」是行為決策，不是實作細節。

**選項**：

- **(a)** **承認 `503` 為合法第三態**：擴充斷言允許集為 `[400, 403, 409, 503]`，並補「503 時終局須為 `DRAFT` ∧ 零快照」之強斷言 ＋ AC-01(c) 之故障注入格。**零 `backend/src` 變更。**
- **(b)** **消除競態**：改動完成流程之交易結構（縮小謂詞鎖範圍／提高重試上限／改隔離等級），使 `503` 在此情境下不再出現；斷言維持 `[400, 403, 409]`。
- **(c)** **兩者**：先做 (a) 使測試誠實，再做 (b) 之低風險子集（**僅提高重試上限與退避上限**，不動隔離等級與鎖範圍），並以前後 N≥30 輪之出現率為物證。

**各選項影響**：

| 選項 | 好處 | 代價／風險 |
|---|---|---|
| (a) | 測試誠實反映契約；零產品風險；**AR-2（503 無測試）一併結清**；成本最低 | 併發下使用者仍可能見到 `503`（**現況即如此**，非新增）；未降低發生率 |

### D4 — 「無引用」判定之封閉來源集　**【High：不可逆刪除之判準】**

**為什麼要決定**：BE-US-25⑥ 逐字為「被**草稿、已完成申請、報表或稽核資料**引用 → 不得刪除」。但**實查結果與該敘述不完全對應**：`schema.prisma` 全案**無任何 FK 指向 `Attachment`**；引用為弱引用且方向相反（`Attachment.refType`／`refId` → 容器）；`Report`／`VoidedReportFile` **零 `attachmentId` 欄位**（PDF 內嵌位元組）。故「報表引用附件」在資料層**不存在**，而「稽核資料引用」只可能以 `AuditLog.summary` 之 JSON 內容形式存在。判定集合直接決定「刪或不刪」，必須人類定案。

**選項**：

- **(a)** **狀態＋容器存在性**：`status=LINKED` 恆保護；`status=TEMP` 且 `refType`／`refId` 指向**存在之容器**者保護。**不查稽核**。
- **(b)** **(a) ＋ 稽核 JSON**：另查 `AuditLog.summary` 是否含該附件 id（`jsonb` 查詢）。
- **(c)** **(a) ＋ 保守寬限**：不查稽核，但把 TTL 之實效門檻拉高（如「TTL 且距最後一次 `updatedAt` 亦逾期」），以時間換安全。

**各選項影響**：

| 選項 | 好處 | 代價／風險 |
|---|---|---|
| (a) | 判定簡單、可完整機械守門；與資料層事實相符 | **與 BE-US-25⑥ 之字面（「報表或稽核資料引用」）有落差**——須以記載型 `it` 明示「資料層無此引用形式」，Gate 須確認此解讀 |
| (b) | 字面覆蓋 US 全部四類 | `jsonb` 全表查詢之成本；**實查：現行各 Phase 之 `summary` 是否真的寫入 attachment id 未經確認**——若從不寫入，此查詢恆為空且永久是死碼；誤判風險（id 字面出現於自由文字） |

**推薦**：**(a)**，並**附兩項義務**：①以 AC-03(b) 之列舉守門證明「今日資料層確實無其他指向 `Attachment` 之欄位」，且**新增即必紅**；②以記載型 `it` 逐字記錄「BE-US-25⑥ 之『報表／稽核引用』在現行資料層不存在對應欄位；若日後新增，(b) 之守門會使其必紅」。**(b) 應在 T3 首步以實查（`AuditLog.summary` 是否曾寫入 attachment id）決定是否加碼**——若實查發現確有寫入，則本推薦自動升級為 (b)，屬**依事實之升級而非降級**，請人類在裁定時一併授權此條件式升級。

### D7 — Cookie 安全屬性集　**【High：認證】**

**為什麼要決定**：NFR-US-11② 逐字為「應使用**安全屬性**，並限制用戶端程式直接讀取」，但未列舉屬性。現行 production 分支為 `{ httpOnly, sameSite:"lax", path:"/", secure:true, maxAge }`（`auth/routes.ts` :51-59）。是否加碼屬**使用者可見之連線層行為**。

**選項**：

- **(a)** **維持現況並釘死**：`HttpOnly ∧ SameSite=Lax ∧ Path=/ ∧ Secure`，以 `toEqual` 封閉守門（**本 AC 之價值在於「從此不可退化」**）。
- **(b)** **(a) ＋ `SameSite=Strict`**。
- **(c)** **(a) ＋ `__Host-` 前綴**（Cookie 名改為 `__Host-sid`）。
- **(d)** **(a) ＋ `SameSite=Strict` ＋ `__Host-` 前綴**。

**各選項影響**：

| 選項 | 好處 | 代價／風險 |
|---|---|---|
| (a) | 零行為變更、零風險；`Secure` ＋ `HttpOnly` 已滿足 US 兩項逐字要求；同源架構（ADR-0001，無 CORS）下 `Lax` 已阻擋跨站 POST | 未取得 `Strict` 之額外邊際 |
| (b) | 略強之 CSRF 邊際 | **`Strict` 會使「從外部連結點進系統」時首次請求不帶 Cookie** → 使用者看到登入頁再被導回，體驗變差；本系統為內部系統、同源、無跨站入口，邊際收益小 |
| (c) | 瀏覽器強制 `Secure` ∧ `Path=/` ∧ 無 `Domain`，防子網域覆寫 | **Cookie 名改變＝既有 session 全部失效**（一次性登出，可接受但須告知）；**開發環境（HTTP）下 `__Host-` 會被瀏覽器丟棄** → 需依環境切換名稱，等於引入「兩個 Cookie 名」之複雜度與 B-12 之無聲失敗風險 |
| (d) | 最強 | 上述兩者代價相加 |

**推薦**：**(a)**。理由：①US 兩項逐字要求（安全屬性、限制用戶端讀取）已由 `Secure` ＋ `HttpOnly` 完整滿足；②本 Phase 之真正價值是**把現況釘死成不可退化的封閉守門**（今日無任何測試覆蓋 production 分支——實查 `auth.test.ts` 僅測 non-production）；③(b)(c) 之邊際收益在同源內部系統上小，而代價（體驗、雙 Cookie 名、開發環境無聲失敗）具體且立即。**若人類重視縱深，建議 (c) 而非 (b)**，並須一併批准「開發環境不套前綴」之分支邏輯與其 B-12 守門。

### D8 — 反向代理信任與 `X-Forwarded-Proto` 之處理　**【High：認證 ＋ 日誌可信度】【平台能力前提】**

**為什麼要決定**：正式環境由平台或 nginx 終結 TLS，後端收到的是 HTTP。若應用需要知道「原始請求是否為 HTTPS」（用於導向、或用於決定 `Secure`），就必須信任 `X-Forwarded-Proto`——而**無條件信任等於讓任何用戶端可偽造**。目前 `frontend/nginx.conf` :24 已轉發該標頭，但後端**未設定 `trustProxy`**（實查 `server.ts` 無該選項），故 Fastify 目前**不採信**。

**選項**：

- **(a)** **維持不信任**：`Secure` 由 `NODE_ENV=production` 單獨決定（現行行為），並以記載型 `it` 明示「本系統不依賴 `X-Forwarded-Proto`；HTTPS 之保證來自部署平台」。
- **(b)** **設定 `trustProxy` 為具體來源**（Docker 網段／平台代理 IP，由 `TRUST_PROXY` env 提供）。
- **(c)** **`trustProxy: true`**（信任任意上游）。

**各選項影響**：

| 選項 | 好處 | 代價／風險 |
|---|---|---|
| (a) | 零偽造面；零新增設定；與現況一致 | `request.ip` 恆為代理 IP（日誌中看不到真實用戶端 IP）——**但本專案日誌本就不記 IP，無實際損失**；無法在應用層做 HTTP→HTTPS 導向（**該導向本就該在平台／nginx 層做**） |
| (b) | 可取得真實用戶端 IP 與協定 | 需知道平台之代理 IP 網段（**平台能力前提未確認**）；設定錯誤會靜默失效或誤信任 |
| (c) | 最省事 | **任何用戶端可偽造 `X-Forwarded-For`／`X-Forwarded-Proto`**；若日後有任何邏輯依賴之（限流、稽核 IP、導向），即成安全漏洞 |

**推薦**：**(a)**。理由：①本系統今日**沒有任何邏輯需要知道原始協定或用戶端 IP**（日誌不記 IP、`Secure` 由 `NODE_ENV` 決定、導向歸平台）；②(b) 需要 repo 內查不到的平台資訊；③(c) 為明確的安全反模式。**(a) 之代價須明確入 §17.1**：「HTTPS 之保證來自部署平台，應用層不驗證」——這是**假設**，Runbook 須載明其失效後果（若平台未強制 HTTPS，應用不會察覺）。

### D9 — 健康檢查之探針集合與 liveness／readiness 分離　**【High：誤判會使部署平台反覆重啟】【平台能力前提】**

**為什麼要決定**：現行 `/health` 只探 DB（`health.ts` :24-58）。PRD :525 要求「健康檢查完善」。但**探針加得越多，誤殺風險越高**：storage 暫時不可寫或渲染器暫時忙碌，都會讓平台判定服務死亡並重啟——而重啟解決不了那些問題。

**選項**：

- **(a)** **維持單一 `/health` ＋ 僅 DB 探針**，但補齊：探針逾時上限、失敗日誌紀律之測試覆蓋。
- **(b)** **單一 `/health` ＋ DB ＋ storage 可寫探針**。
- **(c)** **分離 `/health/live`（行程活著即 200，零外部相依）＋ `/health/ready`（DB ＋ storage）**，compose 與平台各指向適當者。

**各選項影響**：

| 選項 | 好處 | 代價／風險 |
|---|---|---|
| (a) | 零誤殺新增面；改動最小；`docker-compose.yml` :49-58 與平台設定零變更 | storage 掛掉時健康檢查仍綠（**但重啟也救不了 volume 問題**，故此「漏報」實務上無害） |
| (b) | 涵蓋 NFR-US-07 之儲存面 | **探針本身要寫檔**（AC-14(d-1) 之零殘留要求）；volume 暫時滿／權限問題 → 平台反覆重啟 → **服務比不重啟更不可用**；探針頻率（compose 每 10 s）會產生持續 I/O |
| (c) | 語意最正確（liveness 不因外部相依而失敗） | 需同批改 compose healthcheck ＋ Dockerfile ＋ 平台設定（**平台能力前提未確認**）；兩端點之語意須寫入 Runbook 否則日後易誤設 |

**推薦**：**(a)**。理由：①健康檢查之目的是**讓平台知道要不要重啟**——storage 與 DB 之外部故障，重啟皆無助益，反而放大不可用時間；②本 Phase 之真正缺口是「探針逾時上限」與「失敗日誌紀律無測試」，(a) 已完整覆蓋；③(c) 語意雖最佳，但需要 repo 內查不到的平台設定資訊，且引入兩端點之長期維護面。**若人類選 (b)/(c)，須一併批准 T9 升 High 與 compose／Dockerfile 之同批修改。**

### D10 — 效能量測之方法與環境　**【方法論風險；量測結論將成為 D17 之輸入】**

**為什麼要決定**：本專案**無 HTTP 負載量測先例、無負載工具依賴**（§11.6 #2）。量測手法決定「數字代表什麼」——量到的是伺服器內部處理時間、還是含網路與 nginx 的端到端時間，兩者不可互相取代，而 NFR-US-14 之目標（2 s／3 s／10 s）顯然是**使用者感知**的端到端時間。

**選項**：

- **(a)** **真實 HTTP（Node 內建 `fetch`／`undici`）打 compose stack 之 nginx**（端到端，含反向代理）。
- **(b)** **真實 HTTP 直打後端**（跳過 nginx）。
- **(c)** **`app.inject`**（Fastify 內部注入，零網路）。
- **(d)** **引入負載工具**（autocannon／k6 等 npm 依賴）。

**各選項影響**：

| 選項 | 好處 | 代價／風險 |
|---|---|---|
| (a) | 語意最貼近 US（使用者感知）；零新增依賴 | 需 compose stack 就緒（依賴 T10）；量測含 nginx 與 Docker 網路之雜訊；20 併發下**客戶端本身可能成為瓶頸**（單行程事件迴圈）——須 spike 確認 |
| (b) | 排除 nginx 變因，較穩定 | 與使用者感知有落差（須於報告逐字載明「不含反向代理」） |
| (c) | 最確定性、最易重現、可寫成 vitest 測試（**可入 §12 成為測試列而非 Handoff 物證**） | **量不到網路、序列化、反向代理**；「20 併發」在 inject 下之語意是「20 個並行 Promise」，與真實連線壓力不同——**不可宣稱已驗證 NFR-US-14⑤** |
| (d) | 專業工具、統計完整 | **新增 npm 依賴**（違 N-7 之推薦前提，須人類批准）；k6 為非 npm 之外部二進位（違 §1.2 非目標 #5） |

**推薦**：**(a) 為主、(b) 為備援**。理由：①US 之目標是使用者感知時間，(a) 是唯一語意相符者；②零新增依賴；③(c) 雖最方便入 §12，但**用它宣稱 20 併發已驗證會是不誠實的宣稱**——寧可讓該列停在 Handoff 物證。**T11 首步 spike 若證明客戶端成為瓶頸**，正解為 (b) ＋ 於報告逐字載明射程限制，**不得**改用 (c) 後仍宣稱涵蓋 NFR-US-14⑤。

### D11 — 備份技術選型與是否加密　**【High：資料保存】【平台能力前提】**

**為什麼要決定**：備份是本 Phase 之核心交付，其技術選型直接決定**還原是否真的可行**。實查之硬事實：dev 機（Windows）**`pg_dump` 不在 PATH**；`docker` 可用；CI 之客戶端版本相容性未驗證（§11.6 #1）。此外備份含個資（`User`、附件、稽核），是否加密屬資料保存決策。

**選項**（兩個子問題）：

- **D11-1 DB 備份技術**：**(a)** `pg_dump -Fc`（自訂格式，經 `docker exec` 於 postgres 容器內執行）／ **(b)** `pg_dump` 於主機（需客戶端且版本相容）／ **(c)** **邏輯備份**（經 Prisma 讀出全表為 NDJSON）／ **(d)** volume 檔案系統快照（平台能力）。
- **D11-2 是否加密備份**：**(a)** 不加密，改以目的地之存取控制保護（Runbook 載明）／ **(b)** 以對稱金鑰加密（金鑰經 env）。

**各選項影響**：

| 子問題 | 選項 | 好處 | 代價／風險 |
|---|---|---|---|
| D11-1 | (a) | **版本必然相容**（客戶端＝伺服器同一容器）；`-Fc` 支援選擇性還原與平行還原；跨 dev／CI／正式一致 | 需 `docker exec` 可達（**CI 之 service container 可達性須 spike**）；正式環境若用受管 DB（無容器可 exec）則不適用——**須 Runbook 提供受管 DB 之替代指令** |
| D11-1 | (b) | 最直接 | dev 無此二進位（實查）；版本相容性風險真實存在 |
| D11-1 | (c) | **零外部二進位依賴**；跨平台；可完全在 vitest 內驗證 | **不涵蓋 schema／序列／擴充／權限**；還原需先跑 migration；大表記憶體壓力；**「資料庫可開啟」之 AC-23(a) 判準須降級**（`_prisma_migrations` 尾筆改為「業務表列數與關聯相符」）並列 §17 |
| D11-1 | (d) | 最快、最完整 | **完全依賴平台能力**（repo 內無資訊）；本地無法驗證 → 與 PRD :526「在測試環境驗證流程」相衝突 |
| D11-2 | (a) | 簡單；還原時無金鑰遺失風險（**金鑰遺失＝備份全滅**） | 備份檔含個資，目的地若外洩即全洩 |
| D11-2 | (b) | 靜態加密 | **金鑰管理成為新的單點**；金鑰遺失使備份不可用（比不加密更糟）；金鑰須入 env 且**不得**入備份自身（AC-22 之新面） |

**推薦**：**D11-1=(a)**（`docker exec` ＋ `pg_dump -Fc`），**(c) 為 spike 失敗時之替代路徑**（§11.6 #1 已定義三層退路）；**D11-2=(a) 不加密**，改以「目的地之存取控制 ＋ AC-21 之路徑守門 ＋ Runbook 明載存取權限要求」保護。理由：①金鑰管理在本專案規模下引入的風險（遺失即全滅）大於其收益；②US 未要求加密；③若人類要求加密，須一併批准金鑰之保管流程與「金鑰不入備份」之新 AC。

### D12 — 「不與正式同主機／磁碟」在本 Phase 之驗證形式　**【High：資料保存】【平台能力前提】**

**為什麼要決定**：NFR-US-12⑤ 逐字為「不得只存在正式系統相同主機或磁碟」。PRD :526 又明示「異地保存為部署時人工設定」。**兩者之間有一段可機械化的部分與一段不可機械化的部分**，必須劃清，否則會出現「AC 寫了但沒人真的驗」或「宣稱已驗證而其實只驗了路徑字串」。

**選項**：

- **(a)** **只做路徑樹守門**（AC-21(a)：目的地不得為 storage／PG data 之祖先或後裔）＋ Runbook 載明異地為人工設定。
- **(b)** **(a) ＋ 掛載點／裝置檢查**（比對目的地與正式資料之檔案系統裝置 id，不同才放行）。
- **(c)** **(a) ＋ 要求目的地為遠端**（如以 URL scheme 判定 `s3://`／`rsync://`），本地路徑一律拒絕。

**各選項影響**：

| 選項 | 好處 | 代價／風險 |
|---|---|---|
| (a) | 可完全機械化且跨平台；與 PRD :526 一致 | **同一顆磁碟之不同目錄會通過**——US 之「同磁碟」半句未被機械保證，只靠 Runbook |
| (b) | 真的擋住同磁碟 | 需讀取裝置 id（Linux `stat -c %d`／Windows 不同語意）——**跨平台語意不一致**；容器內之裝置 id 對「主機是否同一顆磁碟」並不可靠（bind mount／overlay）；**可能給出虛假的保證** |
| (c) | 最貼近「異地」 | 需引入遠端傳輸能力（新依賴或外部工具，違 §1.2 非目標 #5）；測試環境無遠端目的地可用 → 與 PRD :526「測試環境驗證流程」衝突 |

**推薦**：**(a)**，並**明確記載其射程限制於 §17.1**：「本 Phase 機械保證的是『備份不落在正式資料之路徑樹內』；『不同主機／不同磁碟』之保證來自部署時之人工設定與 Runbook 檢核，**系統不驗證**。」——**這個限制必須寫進 §17 與 Runbook，不得讓 AC-21 之綠燈被誤讀為 US⑤ 已完全滿足。** (b) 之虛假保證比沒有保證更危險。

### D13 — 還原驗證之自動化程度與「主要資料關聯存在」之判準　**【High：資料保存】**

**為什麼要決定**：NFR-US-13① 之三項（DB 可開／附件可讀／關聯存在）中，「**主要資料關聯存在**」沒有定義。判準若太鬆（只查一兩張表）等於恆真；太嚴（全表全外鍵）則成本高且與備份技術耦合。

**選項**：

- **(a)** **七項固定清單**（AC-23(c) 所列：三種子表 1:1、`TripSegment`、`Report`、`VoidedReportFile`、`Attachment` `LINKED` 之容器、`AuditLog.actorId`、`Session.userId`）。
- **(b)** **動態全外鍵掃描**：以 `information_schema` 列舉全部 FK，逐一查孤兒（**手法已於 PHASE-010-T5 實跑成功**）。
- **(c)** **抽樣**：隨機抽 N 筆申請，逐筆驗其完整關聯鏈。

**各選項影響**：

| 選項 | 好處 | 代價／風險 |
|---|---|---|
| (a) | 明確、可讀、Runbook 可逐項對照 | **固定清單會過時**——新增資料表時無人記得更新（與 `PHASE-010.md` D-10 之「無反退化守門」同型缺陷） |
| (b) | **自動涵蓋未來新表**；手法有先例（`phase10-user-delete-regression.test.ts` :41-50） | 需在還原目標之 schema 上執行（`current_schema()` 侷限紀律須沿用）；FK 由 DB 保證，理論上還原後必然成立 → **可能恆真**，須配 AC-23(e) 之破壞性 mutant 才有鑑別力 |
| (c) | 貼近「業務上真的可用」 | 隨機性使失敗不可重現；抽樣可能漏掉問題 |

**推薦**：**(a) ＋ (b) 併用**：以 (b) 之動態列舉作為**完整性守門**（新表自動納入、清單過時即紅——直接解掉 (a) 的老化問題），以 (a) 之七項固定清單作為**Runbook 可讀之對照表**並斷言「七項 ⊆ 動態列舉之結果」。**鑑別力由 AC-23(e) 之「損毀備份必然失敗」承擔**——這一格是整個還原驗證非恆真的唯一證明，**不可省略**。

### 18.4 呈現轉換樣本預確認（治理 2026-08-11.1）

> **判準**：涉「資料呈現轉換」（結構攤平、值轉換、在地化顯示、格式重排）之決策點，提請裁定之材料必附**真實資料之渲染樣本**；無法取得者明標「樣本缺口」並預告 Mock Gate 有推翻風險。

| 決策點 | 是否涉呈現轉換 | 判定依據 |
|---|---|---|

**結論**：**本 Phase 無「資料呈現轉換」型決策點**（結構性原因：零前端變更、Mock Gate 不觸發）。**零樣本缺口**。D10 之邊緣情形已以「報告欄位入 AC ＋ Handoff 附真實樣本」預先處置。
