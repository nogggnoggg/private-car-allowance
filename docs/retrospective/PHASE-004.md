### 3.2 B-30：三個修復回合全部失敗

差旅草稿的每段附件上限（3 張）在併發下可被突破，全套回歸約 **23% 失敗率**。

- T11 一次、T11R 兩次修復（advisory lock 提前、SERIALIZABLE→READ COMMITTED、原子單一 UPDATE）**全部沒關閉**
- implementer 正確觸發 §28「同一 Failure Signature 三回合上限」Stop
- 大總管接手診斷，發現**雙重成因**：
  - **(a) 測試遷移時語意失真**：原 PHASE-003 測試 race 的是**增量式** link 打到 `limit=1` 容器（「只有一方成功」正確）；T11 依 C1 裁定逐條遷移換成**整份取代式 PUT** 後，兩個併發請求各自宣告的都是合法的 3 張，「一方必敗」的斷言**本身就與 D15 語意矛盾**
  - **(b) 真缺陷**：`computeAttachmentDeltas` 的 baseline 在**交易外**（用 `prisma` 而非 `tx`）計算，併發時雙方 baseline 皆為前態、各自只 link 不 detach → 最終 4 張
- 處置：Spec §17 新增 **D19「最後寫入者贏」**（使用者批准）→ 回退兩次失敗嘗試 → baseline 移入交易內 → 斷言依 D19 修正 → 新增 AC-22 鑑別力測試

### 3.3 套件不具決定性（期中 Review M-1，Critical）

失敗率約 **30%**，命中的是本 Phase 最有價值的測試（金額語意、快照不變性、D19 併發）。

**致命處：大總管先前對 T8／T11／T15 的「全綠」驗收是抽到好籤。**

兩個獨立機制：
- **機制 A**：16 個 fork 對單一 Postgres 開真 SERIALIZABLE 交易 → 查詢延遲超出退避視窗 → 6 次重試預算耗盡 → 503
- **機制 B**：參數版本表全域可見性（見 3.1 #4）

修復（R3）：機制 A 以 `maxForks` 減半（**經受控實驗建立因果**：`docker update --cpus 1` 限制 DB 至單核，15 輪重現 4 次；同條件下僅減半即 25/25 全綠）；機制 B 改為斷言前當場查 DB 取全表最早 `effectiveFrom` 再往前退一年。

### 3.4 交易邊界缺陷（期中 Review M-2 / S-1）

`assertApplicationMutable` 只存在於 route 層（交易外），`updateTravelDraft` 與 `deleteApplication` 的交易內 select **沒有 `status`**、全程無狀態守門。

可達序列：PUT 進入 route 通過守門 → complete 的交易提交 → PUT 的交易才開始 → **修改到已完成的申請**，而快照金額仍是舊值 → **申報金額與計算依據不再一致，且完成不可逆**。

最現實的觸發情境不是手速，是 Spec 描述的常規流程：**管理員代編輯草稿、使用者同時按完成**（PUT 是 owner-or-admin，complete 是 owner-only）。

與 B-30 同一類：**守門／基準在交易外算好，交易內不重驗**。修復（R4）時一次列出全部配對收斂，並附帶發現 Prisma 5.22 不把死鎖（40P01）映射為已知錯誤碼、三個重試迴圈皆不認得。

### 3.5 D6 授權漏洞（終審 Review S-1）

D6 定案「草稿／預覽 `computed` **不含**單價」，明文理由是「若附單價等於以另一路徑對一般使用者揭露參數表，屬對 003a D10 已批准授權範圍的實質擴張，**不由 AI 代為放寬**」。

實作在**型別層**忠實落地（`TravelComputedDto` 編譯期即無單價欄位，期中 reviewer 評為模範），但**目的在語意層失效**：回應含每段 `fuelAmount = totalKm × 單價`，而 `tripDate` 與 `totalKm` 皆使用者可控——**送 `totalKm=1` 即得單價本身，4 位小數完全一致**，任意日期可反覆查詢還原整份參數版本歷史。

**專案自己的測試就是證據**：`phase4-travel-preview.test.ts:255-273` 以一般使用者 cookie 送 `totalKm:"1"`，斷言 `fuelAmount === "5.0000"`——該值正是該日單價。

即 **Gate 當初明確否決的 D6(b) 後果實際成立，而 Gate 紀錄以為已避免**。使用者裁定：承認邊界擴張、記入 Spec §17，不改程式；並警示 PHASE-007／008 不得再以「一般使用者不知道單價」為安全前提。

## 4. 根因分析（依影響排序）

### 根因 1：共用可變測試資料庫 + 16-way 平行 + 前綴命名清理

直接生出**全部 6 起隔離事故**與 M-1 機制 A。

**致命的是下游效應**：套件失敗率 30% 時，「跑一輪全綠」不再是證據。大總管因此把驗收門檻從 2 輪一路加到 14 輪、17 輪——**用統計去補結構的洞**。在當下是正確處置，但形成惡性循環：

```
套件不可信 → 加驗證輪次 → 時間爆炸 → 根因仍未處理 → 套件仍不可信
```

而且在發現之前，已經有三個 Task 的驗收建立在運氣上，等於要重來。

**驗證重跑是本 Phase 最大單一時間支出。**

### 根因 2：Spec 遵循度靠人讀，沒有機械檢查

終審抓到的三項全是「文件說 X、程式說 Y」：
- **S-2**：Spec B-23 明文寫「萬用字元視為字面字元（**須有測試**）」——實作不跳脫，測試不存在
- **S-3**：Spec §11.4 列 5 個 E2E 情境，落地約 1.5 個；§11.6 宣稱 E2E 覆蓋的 6 條 AC 在 E2E 層並不存在
- **S-4**：Spec §6.1 L387 與 §9 L766 仍寫 `/complete` 用 `assertOwnershipOrAdmin`，與 D17「不提供代完成」直接牴觸

Spec 自己就有 §11.5／§11.6 列出必要測試清單，**但沒有任何一步去 diff 那份清單與現實**。這類缺口本可在當天發現，卻拖到最後一關由人讀出來。

### 根因 3：Packet 用轉述而非引用

大總管的 AC-41 錯誤與 B-30 的語意漂移是**同一個病**：規範性內容被大總管用自己的話重寫，產生第二個事實來源，而它會漂移。

### 根因 4：Review 太晚

期中檢查點在 10 個 Task 之後才跑，一跑就抓到「套件不具決定性」——那該在第 3 個 Task 就被攔下。M-2（守門在交易外）在 T3/T4 就已存在，卻到第 10 個 Task 後才被讀出來。

### 根因 5：大總管既是派工者又是唯一驗證者

結構性單點瓶頸。所有回歸重跑、所有靜態核對、所有 commit 都經過同一個角色。

## 5. 建議（依槓桿排序）

### ① 測試隔離改成結構性，不靠命名慣例
每個 worker 一個 schema 或一個 DB，或每個測試包在可回滾交易裡。

**一項消滅六類事故**，並且讓「跑一輪」重新成為證據——驗證輪次可從 5~17 掉到 1~2。**這是唯一能大幅壓縮總時間的改動**，其餘皆為邊際改善。

### ② AC ↔ 測試對應機械可查
Spec 已列 AC 與必要測試，缺的是可執行的映射與「哪些 AC 沒有測試守住」的報告。S-2／S-3／S-4 那一整類會當場現形，而非拖到終審。

### ③ Packet 只准引用原文＋行號，禁止轉述規範
規範性內容一律貼原文，不得用大總管自己的話重寫。

### ④ 驗證證據改成固定腳本的輸出
現在是「請貼三個數字」，結果出現三次不實。改成一支腳本產生的區塊，implementer 貼、大總管跑同一支——消滅整類問題，順便省掉大量手動重跑。

### ⑤ High 風險 Task 交付當下就過一次輕量 review
M-2 這種「守門在交易外」的缺陷測試抓不到，只有人讀得出來。晚抓一個 Task 就多一份連帶。

### ⑥ 把「驗證」獨立成一個角色
解除大總管的單點瓶頸。

## 7. 結論

**本 Phase 的成本，約八成來自「測試環境的結構」而非「AI 協作的結構」。**

agent 架構本身（派工／Stop／獨立 review／人類 Gate）這次抓到的東西比它花掉的多；真正該動手術的是**測試基礎設施**與 **Spec 遵循度的機械化**。

有些成本則是必要投資，不應砍除：B-30 最終證明是真缺陷，且它揭示的「守門／基準在交易外算好、交易內不重驗」模式後來又生出 M-2 與 S-1；六起測試隔離事故清掉的是**既有地雷**而非新債。
