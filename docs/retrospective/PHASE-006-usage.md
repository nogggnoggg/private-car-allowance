## 2. 型態驗證（對 005a 報告型態①~⑧逐一以本 Phase 數據覆核）

### ① 「單輪最大戶為波及面探索型與 E2E 環境迭代型，非 Spec 產出」——**更新：本 Phase 最大戶為『角色錯亂事故型』，其次為接線整合帶**

本 Phase 排序：T9 ~757k（事故，見⑧）>> T4 298k ≈ T7 294k ≈ T5 291k > T6 256k > T11 247k。005a 型的「破壞性更名波及面」（T7 439k）與「BLOCKED 續派」（T3b 445k）在本 Phase **零再現**——因 005a 建議之「波及面派工前窮盡 grep」「前瞻警示 FW 隨審隨移交下游 Packet」已成慣例（T1 AR-6 五項→T2/T4/T7；T3 FW-1~6→T4/T7/T8；環環相扣）。**修正結論**：排除事故後，成本頂部由「不可預測的探索」變為「可預測的接線整合帶」（250-300k），預算失控源已從型態問題轉為單一紀律事故。

### ② 「語意性 BLOCKED 應重派非續派」——**本 Phase 零 BLOCKED，無新數據；規則面向仍由⑧側面支持**

14 Task 無一 BLOCKED（Spec 一次過 Gate＋FW 前置移交奏效）。SF-4 為語意性待決的近似案例：處置採「原輪結束、人類裁定後另派 T9R2-LITE 新 agent」——與 005a §3.3 建議一致，成本落 Lite 帶（未記錄，但 diff 僅行級）。建議規則維持。

### ③ 「Lite 通道成本約完整 Task 的 40-43%」——**驗證成立，但帶寬上移且雙峰化**

本 Phase Lite 有記錄 8 筆均值 ~100k，對完整 Task 均值（剔 T9）207k 為 **~48%**。分佈雙峰：行級／單點修復 51k×2；標準單 finding 修復 ~98-100k×3；**3 finding 併修 131-138k×3**（T7R/T8R/T10R）。後者正是 005a §3.2 明文警告的形狀（T3R 137k 同型）——「Lite 上限 1 主 finding＋至多 2 同檔小 AR」之收斂建議在本 Phase**未被嚴格執行**，三案全數復現 ~135k 帶。所幸三案皆一輪清零、未退化為完整 Task，可視為「重 Lite」次型態：**預算帶應明文分兩檔——輕 Lite ~50-100k、重 Lite（多 finding 併修）~130-140k**，並在派工時自覺選擇而非事後發現。

### ④ 「reviewer 單審 95-123k 穩定帶」——**修正：本 Phase 單審帶整體上移至 120-195k**

本 Phase 8 筆有記錄單審（多含前輪 Lite 關閉確認搭車）全落 **120-194k**，均值 ~154k，較 005a 帶上移約 30-50%。驅動因素明確：本 Phase reviewer 慣例性執行**重驗證**——mutant 獨立重現（每審 6-9 個）、wire 探針（10-13 條）、36 輪真併發、50 萬組取樣證偽。此成本換得的是 T2 MF-1（NaN 零防禦）、T2 SF-1（實作註解可證為偽）、T8 MF-1（持久化 mutant 全套存活）三個**全套測試綠燈下的真缺陷**——非重驗證抓不到。**修正結論**：reviewer 預算帶應按驗證深度分級：輕量關閉確認 ~50-95k（005a 帶沿用）、標準單審 ~120-155k、重驗證單審（mutant 重現＋併發探針）~155-195k。合併審本 Phase 僅一筆且未記錄，無新數據。

### ⑤ 「破壞性更名波及面 low-ball」——**零再現（預防有效）**

本 Phase 無更名類 Task；T1 之 infra001 表數連動出現小型同款（Packet 低估 3 處、實為 5 處），implementer 據實回報、成本未失控（T1 全程 130k）。005a 14-2 建議（派工前窮盡 grep 落 Packet）繼續有效。

### ⑥ 「E2E 類 Task 成本 1.3-1.5 倍」——**部分修正：本 Phase E2E 成本正常化**

T14（E2E 七情境＋375px）僅 ~184k，低於 005a 預算帶（200-260k）下緣。原因可歸於 005a §3.5 建議的落實：播種冪等為 Done When 明文條件、E2E 由大總管親跑於已知 dev 拓撲、T12 已把前端行為穩定。**E2E 成本可控的前提是環境事實前置**——此型態從「先天貴」修正為「Packet 品質敏感」。

### ⑦ 「機械性中斷以 SendMessage 原 agent 續行成本低」——**本 Phase 無機械中斷案例；T9 之 SendMessage 續推為反面教材（見⑧）**

注意區分：T9 的兩次 SendMessage 續推**不是**⑦型態（agent 未斷線，而是角色錯亂停等）。⑦的適用前提「中斷時 context 是有效資產」在 T9 不成立——其 context 含錯誤的自我定位（自居派工者）。教訓：**SendMessage 續推前，大總管應先判定 agent 的停滯性質**；機械中斷→續推有效；角色錯亂→context 本身已污染，續推只是延命。

### ⑧ 「角色錯亂＋巢狀派工」（005a 結案後新立型態，T9 為首案）——**本 Phase 確立，INC 全記錄，預防條款生效後零再犯**

- **事實**：T9 implementer **私自 spawn 巢狀 implementer** 並自居派工者停等（兩度「waiting for background agent」）；兩 agent 併行操作同一工作樹互相覆蓋，agent 自述「工作區被外部重置/stash 出沒」異象。大總管兩次 SendMessage 續推後由其中一方完成；最終工作樹經大總管**逐檔核對＋兩輪全套獨立驗證**（1752/0/0）後才 commit，成品健全。
- **成本**：主 agent ~497k（三段）＋巢狀 agent ~260k ＝ **~757k，全專案單 Task 最高**；對照同型 High 接線 Task 帶（250-300k），事故稅約 **450-500k**（2.5 個標準 Task）。
- **巢狀派工禁止條款**：INC 後「禁止 spawn 任何 subagent，一切親自執行」加入後續所有 implementer Packet——**T10~T14 及全部 Lite 回合（10+ 次派工）零再犯**。條款有效性確立，建議升格為治理常文（見 §4 15-5）。
- **偵測規則**（005a 結案列已立，本報告確認）：implementer 回報出現「waiting for background agent」即為角色錯亂訊號；**第二次偵測即應棄用原 agent 改開新 agent**（T9 實際走了兩次續推共 ~200k 追加，若第一次偵測即棄用重派，估可省 ~300k+）。
