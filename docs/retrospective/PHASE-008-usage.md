## 2. 型態對照與預算帶校準

### 2.1 007 帶對 008 之系統性檢討

007 §3／§6.3 帶在 008 的表現呈**清晰二分**：

- **成立側**：純函式 BE（T2 111／T3 127 vs 帶 145-160——甚至低於帶）、FE 頁面（T12 139／T13 183 帶內）、E2E（T15 204 帶內）、守門型（T8a 100／T17 121 帶內）、reviewer 各級帶、暖續派增量帶——**凡 007 有 ≥2 數據點的型態全數續驗成立**。
- **失準側**：DB 安全網（T1 297 vs 130-135＝2.2×）、揭露面資料組裝／版型（T4 329／T5 278 vs 160-200）、接線端點（T9 287／T10 331 vs 160-200）、大接線（T8 444 vs 210-310）、多項合併（T1b 210／T11 304）、方法論首用 E2E（T14 鏈 485 vs 185-265）。共同特徵：**證明義務密度**（mutant 自證、矩陣覆蓋、FW 核銷表、紅燈實錄）成為主要成本駆動，而 007 帶按「diff 規模×層別」估價未計入此項。008 的 FW 鏈愈長（T8 十九條核銷）、上游移交愈多（T11 六項），超帶愈劇——**007 §3 之 14-5 先行訊號（觸檔 ≥6 或 FW ≥8 即評估拆分）被 T8 以 9.6×帶上緣的代價再證，但本 Phase 未執行該訊號**。

## 3. 異常與教訓

### 3.1 T8 鏈 ~2.97M（單 Task 鏈全專案新高；佔全 Phase ~22%）

組成：T8 444k→即審＋三難矩陣→人類裁定方案 (d)→SPEC-REV-T8→T8R 312k→（複審）→T8R2 234k（MF-2/3 交易 timeout）→T8R3 413k（顧問鎖→三層複現證偽）→人類再裁定→T8R4 555k（READ COMMITTED）＋審四輪 ~1,010k。

**成本歸因（三層，非 implementer 低效）**：
1. **Spec 設計衝突於實作期才暴露**：D3（配號最後步）⇔AC-15（列印/PDF 同 HTML 全等）⇔AC-11（列印版含編號）三難為產品可見行為抉擇，Spec 自查未攔——T8 主輪之後的整條方案 d 鏈（~2.5M）都是這個衝突的解決成本。
2. **併發機制迭代**：顧問鎖於 SERIALIZABLE 不成立（大總管推薦錯誤已認錯記 §18）→隔離等級再裁定——兩輪防呆攔截（SF-5 P2034 據實紅燈／T8R3 三層複現）確保錯誤機制**未落地**，攔截本身是鏈中最有價值的環節。
3. **拆分線失守**：T8 預估 210-310k、實測 444k 越 320k 拆分線且未中途 BLOCKED 回報；T8R 312k 微越再記。

**教訓**：①大接線型預拆（§2.3）；②Spec 期加「跨 AC 一致性自查」攔三難型衝突（建議 §5）；③併發／隔離等級類機制在 Spec 期以最小 spike 驗證可行性，勿以整輪 Task 為驗證載體。

### 3.2 T14 鏈——BLOCKED 方法論證偽型（首輪 ~392k/148＋T14b ~93k）

§11.4 假設 `emulateMedia({media:"print"})` 可觀察 `break-inside`——implementer 探針證偽（Blink 僅於真實列印管線分頁）；改走 PDF 文字擷取又撞 Windows 開發機 Type3 字型內嵌之環境特異。**成本歸因＝Spec 方法論錯誤，非 implementer 低效**：首輪 392k 中 AC-13(b)/AC-34 已完成綠燈、自建之零依賴 PDF 解析器成為 T14b 幾何法（+93k 即落地）與 reviewer 交叉核對的共同資產；若 implementer「硬凹」以恆真 DOM 量測交綠燈，該假綠將直達生產。**教訓**：Spec 引入首次使用之量測／驗證手段時，須以最小 spike 驗證或明標「方法論風險」並取預算上緣（SPEC-REV-MOCK 之 small-icu 決定性警告為同型風險的正面示範——事前寫進 Spec 不變式，MOCK-R1 一次做對）。

### 3.3 超帶未即時回報之程序偏差（×多次）

Spec §15 明文「逾預算 50% 須即時回報（Stop Condition）」，但本 Phase 至少六件為「完工後才發現／揭露超額」型：T8（444k 越拆分線）、T8R（312k 微越）、T1（2.2×）、T1b（+50%，結案裁定原文點名「完工時才發現超額 vs 即時回報之程序偏差記回顧」）、T10（+65%）、T11（+71%）。T4（+65%）與 T5（+39%）亦同型。**結構性原因（推定）**：implementer 對自身 usage 無觀測儀表，「即時回報」條文缺乏可操作的觸發器——此為機制缺陷而非個別 agent 紀律問題，修法屬治理討論範圍（§5 建議 #3）。

### 3.4 期中複審 #2 鏈與 MOCK Gate 反饋鏈——多輪小修型態

期中 #2 鏈：主輪 199k→SF-1 升人類裁定（含兩輪白話討論之溝通紀律記錄）→SPEC-REV-T6 136k→T6R 199k→T11R 133k→結案增量 55k→AR-11/12→T6R2 134k→輕量輪增量 17k。MOCK 鏈：SPEC-REV-MOCK 174k→MOCK-R1+R1b 174k→MOCK-R2 71k→合併複審 136k→MOCK-R2b 82k→關閉 12k。**型態結論**：Gate/複審反饋走「Spec 修訂→小修→輕量複審」的固定五步，單修 58-199k、複審 69-136k、關閉增量 12-55k——**輕 Lite 快週轉（T13R 58k 一日內閉環）與重 Lite 誤判（T6R 名義輕 Lite 實測 199k——fixture 重建＋三分支重構應判重 Lite）並存**，檔位判定失準記校準。MOCK 全鏈 12 mutant 全紅之閉環品質值得沿用（Spec 增補即附契約不變式四點，讓 implementer 一次做對、複審僅 1 Must）。
